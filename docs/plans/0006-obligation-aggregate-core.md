- Status: Done

## Goal

Introduce the DDD `Obligation` aggregate root and its core domain behavior, persistence mapping, and aggregate repository without implementing recurrence, reminders, or the full HTTP CRUD surface. Add the first business migration for `obligations`, preserving per-user ownership and the existing PostgreSQL/snake_case conventions.

- Application: Add the aggregate repository port (`IObligationRepository`) and the application-facing contracts needed to load/save an aggregate; no controller or endpoint implementation in this task.
- Infrastructure: Add `PomDbContext.Obligations`, EF configuration, repository implementation, and an EF Core migration for the obligations table and indexes.

- Frontend: Untouched.
- Tests: Add domain unit tests and Infrastructure/API integration coverage for persistence and user isolation.
- Documentation: Update `docs/DOMAIN.md` and `docs/DATABASE.md`; add a decision entry only if the category-FK migration ordering or another meaningful trade-off is resolved.

## Schema changes

Add `obligations` with:

- `id uuid` app-assigned primary key
- `user_id uuid not null` referencing `users(id)`
- `type`, `title`, `notes`, `start_date`, `due_date`, `end_date`
- `status` defaulting to `Pending`
- `priority` defaulting to `Medium`
- `extra_fields jsonb not null default '{}'`
- `is_recurring boolean not null default false`
- `created_at`, `updated_at`, and nullable `deleted_at`, all UTC timestamps

Add the minimum ownership/query indexes from `docs/DATABASE.md` (`user_id/status/due_date` and `user_id/type`, plus any FK index generated by EF).

Open schema question requiring resolution before implementation: `category_id` is required in `DOMAIN.md`/`DATABASE.md`, but the `categories` table is task `0007`. The implementation must either:

1. create `category_id` as nullable in `0006` and make it required/add the FK in `0007`, or
2. move the category table/constraint into this migration, which would overlap task `0007`.

The chosen option must be recorded in `docs/DECISIONS.md` and reflected in the docs. No `recurrence_rules`, `obligation_occurrences`, `reminders`, or `notification_log` tables belong in this migration.

## Implementation outline

1. Confirm the aggregate boundary and invariants against `docs/DOMAIN.md`: required title/due date, valid date range (`start_date <= due_date <= end_date` where applicable), default status/priority, and legal transitions for complete/skip/archive/postpone.
2. Implement the pure Domain aggregate with factory and behavior methods that raise domain events for meaningful transitions where the existing event infrastructure supports them; do not put persistence or HTTP concerns in Domain.
3. Define `IObligationRepository` around the aggregate root (get by owner/id, add, update, and query primitives needed by later use cases). Repository methods must require/use `UserId` so ownership cannot be accidentally omitted.
4. Add EF mapping using existing `PomDbContext.ConfigureOptions` snake_case conventions, UTC timestamp columns, enum string conversions, JSONB `ExtraFields`, app-assigned Guid keys, and the selected category-FK ordering.
5. Implement the Infrastructure repository with every read/update/delete query scoped by `userId`; return not-found semantics for another user’s aggregate rather than leaking existence.
6. Generate and apply the reversible EF migration against disposable PostgreSQL. Verify the model snapshot and migration contain only the intended obligations schema.
7. Add unit tests for creation defaults, validation, transitions, soft-delete behavior, and domain event emission. Add integration tests for migration/persistence round-trip and explicit User A/User B isolation.
8. Update domain/database documentation and log any meaningful schema or aggregate decision immediately.

## Risks / open questions

- Category ordering is the primary blocker: do not implement a required FK to a table that does not exist yet without resolving the choice above.
- `ExtraFields` is JSONB but type-specific validation belongs to the Application layer; this task should only guarantee a non-null object-shaped payload/default and must not grow a second type system in Domain.
- `updated_at` needs a consistent update policy (application-side timestamp or EF save interceptor). Choose the smallest approach compatible with current infrastructure and document it if it becomes a durable convention.
- Domain-event dispatch is documented architecturally but may not yet have a shared dispatcher. If no dispatcher exists, keep event definitions/collection aggregate-local and defer dispatch wiring to the first application use case; do not add unrelated infrastructure.
- No API endpoint is part of `0006`; avoid duplicating the CRUD contract scheduled for `0008`.
- Money remains inside `ExtraFields` as integer Rial values; do not add decimal/float columns or a separate financial entity.
